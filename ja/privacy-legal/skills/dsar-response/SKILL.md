# /dsar-response

1. `~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` を読み込み → DSAR プロセス(システムリスト、検証方法、SLA)。
2. 下のワークフロー実行。
3. リクエストタイプ分類。エスカレーション・トリガーをチェック — 該当するなら進行前にルーティング。
4. 進行: 本人確認 → システムリスト巡回 → 例外分析 → ドラフト。
5. 応答ドラフト出力。送信は**しない** — 人間がレビュー・送信。
6. ハウスプロセスに従って DSAR をログ。

**リクエスト貼り付け前:** リクエストはデータ主体の PII を含みます。セッションと出力ストレージがデータ取扱要件を満たすか確認。不要なもの(ID 添付、無関係なメールスレッド)は墨消し。主体名をファイル名に保存しない。

```
/privacy-legal-ja:dsar-response
[リクエストメールを貼り付け]
```

# DSAR 応答ドラフト

## 案件コンテキスト

**案件コンテキスト。** プラクティスレベル CLAUDE.md の `## 案件ワークスペース` をチェック。`Enabled` が `✗`(インハウスユーザーのデフォルト)ならこの段落の残りをスキップ — スキルはプラクティスレベルコンテキストを使い、案件機構は不可視。有効でアクティブ案件が無いなら問う: 「これはどの案件? `/privacy-legal-ja:matter-workspace switch <slug>` を実行するか、`practice-level` と言ってください。」アクティブ案件の `matter.md` を案件固有コンテキストと上書きとして読み込み。出力は案件フォルダ `~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/matters/<matter-slug>/` に書く。`Cross-matter context` が `on` でない限り他案件のファイルを決して読まない。

---

## 目的

DSAR には期限(適用 regime が設定)、プロセス(検証、ロケート、例外評価、応答)、間違えうる箇所がたくさん。このスキルは各ステップを一通り進め、応答をドラフト。

## 法域前提

この分析は設定で指定された法域スコープを想定。プライバシー規則、応答期限、法的根拠は法域(GDPR vs 州コンシューマプライバシー法 vs セクター)で実質的に異なる。データ主体、処理活動、または管理者が設定と異なる法域にいるなら、この分析はそのまま適用されない可能性。

## プロセスを読み込み

`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` → `## DSAR プロセス` を読む。そこには:
- システムリスト(ユーザーデータが存在するすべての場所)
- 本人確認方法
- 応答 SLA
- 通常対応者 vs エスカレート対応者

システムリストが空または古いならフラグ — どこを見るか知らずに完全な DSAR は不可能。

## ワークフロー

### Step 1: リクエストを分類

データ主体が行使する権利を識別。一般的なカテゴリ:

- **アクセス** — 自分のデータのコピー + 処理に関する情報
- **削除 / 消去** — 自分のデータを除去(例外あり)
- **ポータビリティ** — マシン可読形式でのデータ
- **訂正 / 修正** — 不正確データの修正
- **異議** — 特定処理の停止(多くはマーケティング)
- **制限** — 紛争係属中の処理一時停止
- **販売/共有/自動意思決定からのオプトアウト** — regime 固有の権利

**進行前に適用規則を調査。** 行使された各権利について、適用法律の法域(GDPR, UK GDPR, CCPA/CPRA, 他の米国州プライバシー法、セクター regime)を識別。支配的な制定法または規則をピンポイント参照で引用 — 具体的な条文/セクション、権利のスコープ、カーブアウト。施行日に注意; データ主体の権利は頻繁に改正(毎立法会期で新しい州法)。確認していない規則を述べず、不確実性をフラグして弁護士検証へエスカレート。

> **サイレント補完なし。** 設定済み法律研究ツールへのクエリが当該法域の権利、例外、または期限について結果が少ないか皆無なら、見つけたものを報告し停止。許可なしにウェブ検索やモデル知識でギャップを埋めるのは**しない**。述べる: 「検索は [tool] から [N] 件返した。[regime / right] のカバレッジは薄いように見える。オプション: (1) 検索クエリを広げる、(2) 別の研究ツールを試す、(3) ウェブ検索 — 結果は `[web search — verify]` タグ付き、依拠前に原典でチェックすべき、(4) 未検証としてフラグし停止。どれにしますか?」より低い信頼度の情報源を受け入れるかは弁護士が判断。
>
> **出典帰属の階層化。** すべての引用に出典タグを付ける。モデル知識引用には、単一の「verify」タグではなく 3 階層のいずれかを使用:
>
> - `[settled]` — 安定的でよく知られた制定法・規制への参照で変更可能性が低いもの(例: GDPR Art. 33、CCPA § 1798.100、FTC Act § 5、§ 1798.130(a)(2) 下の 45 日 CCPA 応答ウィンドウ概念)。提出前にはまだ検証、ただし優先度低。
> - `[verify]` — 実在するが検証すべきモデル知識引用: 具体的な実施規則、規制機関ガイダンス、判決、閾値、施行日、2023 年以降の改正。
> - `[verify-pinpoint]` — ピンポイント引用(具体的なサブセクションレター、巻/ページ番号、段落番号、規制サブパート参照)は捏造リスクが最高で、**常に**原典に照らして検証すべき。
>
> ツール取得引用は出典タグを維持(`[Westlaw]`, `[issuing authority site]`, または MCP ツール名); ウェブ検索引用は `[web search — verify]` のまま; ユーザー提供引用は `[user provided]` のまま。階層化により実際の検証作業が明確になる — すべてを検証する読者は何も検証しない。タグを剥がしたり潰したりしない。

リクエストの中には組み合わせも — 「アカウントを削除して、その前にデータを送って」は削除 + ポータビリティ。2 つの連結リクエストとして扱う。

### Step 2: 本人確認

`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` の方法に従う。一般的なアプローチ:

- **ログイン検証:** リクエストが認証セッション内から → 本人確認済み
- **メール一致:** リクエストがファイル上のメールから → 低リスクリクエストには通常十分
- **追加検証:** 高価値アカウントや削除リクエスト → チャレンジ質問、電話確認、ID 文書

**リスクに合わせて調整。** 過剰検証は DSAR プロセスを障壁にする(規制機関への印象が悪い)。検証不足は他人のデータを詐欺師に渡すリスク。

本人確認できないなら:

```markdown
本リクエストが対象となる個人本人からのものであることを確認できませんでした。
進行のため、[verification step] してください。確認できないリクエストへの応答
としては個人データを提供できません。
```

これは時計を一時停止(議論あり)、ただし放置せず — 29 日目ではなく数日内に検証必要と返答。

### Step 3: データを探索

`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` のシステムリストをウォーク。各システムについて:

| システム | 照会済み? | データ発見? | 内容 |
|---|---|---|---|
| 本番データベース | | | |
| 分析(Mixpanel, Amplitude 等) | | | |
| サポートチケット(Zendesk 等) | | | |
| CRM(Salesforce, HubSpot 等) | | | |
| メールマーケティング(Marketo 等) | | | |
| ログ | | | |
| バックアップ | | | (注: 通常削除から免除 — 下記参照) |
| 第三者処理者 | | | (削除のため通知必要かも) |

B2B 処理者の場合: 「データ主体」は通常*顧客の*エンドユーザー。これが実際に自社で扱う DSAR か、顧客が扱うものかをチェック。多くの処理者 DPA は「DSAR は管理者に転送」と言う。

### Step 4: 例外分析

すべてが提供/削除されるわけではない。**進行前に適用規則を調査。** 各項目について、適用 regime 下で誠実な根拠がある例外を識別(例: 第三者プライバシー、秘匿特権、営業秘密、セキュリティ、保持の法的義務、法的請求の確立/防御、取引上の必要性、バックアップローテーション配慮、表現の自由)。支配的な制定法、規則、判例をピンポイント引用。例外スコープは法域と regime で異なる — 最新性を検証し、不確実性をフラグ。

**主観的判断でリストを絞らない。** スキルは誠実な根拠がある例外を提案し、不確実なものをフラグ; 弁護士が応答送付前にリストを絞る。後で適用すると判明する例外を落とすのは高くつく — 一度開示すると、例外は実質的に失われる。妥当な例外の過剰主張はレビューで弁護士が訂正可能。回復可能な誤りを優先。

提案された各例外に明示的注記: **「提案 — 主張前に弁護士レビュー要。規制機関は包括的例外主張を精査するため、弁護士がリストを絞る; スキルはしない。」**

進行中の繰り返し質問:

- レコードには*他の*人々に関するデータが含まれ、提供前に墨消しが必要か?
- 削除を阻む具体的な法的保持義務があるか? 引用すること。
- この個人のデータをカバーする訴訟ホールドがアクティブか?
- 文書化が必要なバックアップローテーションや技術的実現可能性配慮はあるか(一般的な言い訳としてではなく)?

**主張するすべての例外を文書化。** 規制機関が「なぜ削除しなかったか」と問うとき、「法的義務があった」には引用が必要。

### Step 5: 応答ドラフト — 2 通のレター

> **研究コネクター・プリフライト。** どちらかのレターまたは内部例外分析を出力する前に、このセッションで法律研究コネクターが到達可能かチェック — Westlaw、EUR-Lex / 規制機関サイトコネクター、または事務所設定の研究 MCP。これを CLAUDE.md `## 出力 (Outputs)` の reviewer note に集める — reviewer note は内部の例外分析とカバーメモに付き、データ主体への外向き DSAR レターには**付かない**。Step 1(権利分類)、Step 4(例外分析)、または期限管理リサーチステップでコネクターが結果を返さない(または実行時に設定されていない)なら、内部 reviewer note の **Sources:** 行に記録 — 例: `not connected — cites from training knowledge; claimed exemptions, response deadlines, and extension mechanisms are especially fabrication-prone, verify before asserting any exemption to a data subject or regulator`。引用ごとの `[model knowledge — verify]` タグはインラインに残る。出力上に独立したバナーを出さない。

大半の regime は実質応答と別に迅速な受領通知を期待(または要求)。両方生成; 45 日締切まで待つ 1 通のレターに統合しない。

- **Step 5a — 受領通知レター。** 受領から数日内に送付(目標: 当日 〜 3-5 日、regime の法定ウィンドウ内に十分余裕)。受領を確認し、管理者がリクエストをどう理解しているか、応答時計と目標日、未解決の本人確認資料があれば依頼。実質開示を**含まない**。迅速な受領通知は DSAR プロセスが機能している最初の規制機関可視シグナル; 重複リクエストや早期苦情のリスクも低減。
- **Step 5b — 実質応答レター。** 実際の開示、削除確認、ポータビリティエクスポート。法定期限(または内部 SLA が厳しいならそちら)までに送付。本人確認完了後、かつ Step 3 / Step 4 のデータロケート + 例外分析完了後。

**データ主体にどちらかのレターを送るに進む前に:** `~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` の `## 利用者` を読む。役割が Non-lawyer なら:

> DSAR 応答送付は法的影響あり — 内容、主張された例外、省略はすべて規制機関にレビュー可能、誤記は執行リスクに。弁護士とレビュー済みか? Yes なら進行。No なら、弁護士に持ち込むブリーフ:
>
> [1 ページサマリーを生成: データ主体、行使された権利、適用 regime、システムリスト全体でロケートしたもの、どの例外で何を留保するか、本人確認姿勢、応答期限、レター送付前に弁護士に問うべき 3 つ。]
>
> あなたの法域で免許のある弁護士・solicitor・barrister・他の正式な法務専門職を探すなら: 専門規制機関の照会サービスが最速の出発点(US の state bar、英国 (Eng & Wales) の SRA/Bar Standards Board、スコットランド/NI/アイルランド/カナダ/オーストラリアの Law Society、または該当法域の同等機関)。

明示的な yes なしにこのゲートを通過しない。

> **注意:** DSAR レター 2 通はデータ主体に送付する外向き成果物。どちらにも `~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` の `## 出力 (Outputs)` からの work-product ヘッダーを**含めない**。レターに付随する内部メモ、ログ、例外分析は弁護士成果物 — それらは別に保持し、`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` の `## 出力 (Outputs)` に従って work-product ヘッダーを冒頭に付与(ユーザー役割で異なる — `## 利用者` 参照)。

> **どちらかのレターを送る前に:** これは弁護士レビュー用のドラフトで、送付するための応答ではない。送付は管理者をポジションにコミットさせ、例外を放棄させ、規制機関の時計を開始させる可能性あり。免許ある弁護士がデータ主体に送る前にレビュー、編集、承認する。未レビューで送信しない。

### Step 6: ログ

DSAR は監査対象。記録:
- 受領日
- 本人確認日
- 応答日
- 提供/削除内容
- 主張した例外と根拠
- 担当者

## エスカレーション・トリガー

`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` → エスカレーション表に従い、次の場合エスカレート:

- リクエストスコープが異常(「自分についての内部コミュニケーションを含むすべてのデータ」)
- この個人のデータに訴訟ホールド(削除リクエスト + 訴訟ホールド = 矛盾、弁護士が判断)
- 請求者が以前の DSAR 応答に異議
- 規制機関が cc または言及されている

## 期限管理

**2 通レタールール。** すべての DSAR は受領通知レター(迅速 — 受領後当日〜3-5 日目標)と実質応答レター(法定期限まで)を生成。大半の regime は実質応答と別の迅速な受領通知を要求または期待; 45 日目に送る 1 通の統合レターは実質的に正確でもプロセス失敗。

**行使された具体的権利と適用法域について、現在運用中の応答期限を調査。** 延長メカニズムの有無、買える追加時間、データ主体への通知要件をチェック。時計の起点(受領 vs 検証 vs その他 — デフォルトは受領、regime ごとに検証)。支配的な制定法または規則をピンポイント参照で引用。施行日に注意 — データ保護応答タイムラインは頻繁に改正され、新州法は独自の時計を導入。

`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` → `## DSAR プロセス` が法定期限より厳しい内部 SLA を記録しているなら、内部 SLA を使い、法的バックストップを注記。

延長が必要そうなら、初回期限のかなり前に「追加時間が必要」通知を送る。当日延長は印象悪い。

## このスキルがしないこと

- システムを直接照会しない。チェックリストをウォーク、実際の照会は人間(または接続済みツール)。
- 微妙なケースの例外判断をしない。弁護士用にフラグ。
- 応答を送信しない。ドラフト、レビュー、人間が送信。
