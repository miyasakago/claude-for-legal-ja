# /policy-monitor

**スイープモード**(引数なしまたは `--sweep`):
1. `~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` を読み → 出力フォルダパス、ポリシー文書、最終スイープ日。
2. 下のワークフロー実行。最終スイープ以降のファイルを出力フォルダでスキャン。
3. 各出力について: 承認された実務を抽出 → 現行ポリシーコミットメントと差分。
4. ギャップを分類: REQUIRED(ポリシーが現実務を誤表現) vs ADVISABLE(ポリシーが沈黙)。
5. 各ギャップ: 現行ポリシーを引用、ギャップを記述、推奨文言をドラフト。
6. `~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` の最終ポリシースイープ日を更新。

**直接照会モード**(説明引数付き):
1. `~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` を読み → 現行ポリシーコミットメント + 実際のポリシー文書。
2. 提案された実務をパース。ポリシーに対して差分: データカテゴリ、目的、第三者、保持、ユーザー権利、開示。
3. 出力: カバー済み / 欠落 / 抵触 + 各ギャップへの推奨文言 + タイミング推奨。

**スケジュール:** 独自スケジューラー(カレンダー、タスクマネージャー、CI)で `/privacy-legal-ja:policy-monitor` を週次実行するリマインダー設定。スケジュール実行には scheduled-tasks 連携が必要、このプラグインに同梱されていません。

```
/privacy-legal-ja:policy-monitor
/privacy-legal-ja:policy-monitor "オンボーディングメールのパーソナライズに行動データを使い始めたい"
```

# プライバシーポリシーモニター

## 目的

プライバシーポリシーは実務から一方向に乖離する: 実務が前進、ポリシーが遅れる。PIA が新データカテゴリを承認。DPA がどこにも記載のない副処理者と署名。トリアージ結果が新ユースケースを条件付きとマーク、ポリシーがまだ作っていない開示要件付き。数ヶ月後、ポリシーを読んだ人がそれは実態と合わないと気づく。

このスキルは問題になる前に乖離を捕まえる — 出力フォルダを週次クロールするか、直接質問「X を始める、ポリシーにとって何を意味する?」に答える。

出力は常に同じ: ギャップ、推奨文言。

---

## 現状を読み込み

`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` を読む:
- `## 自社紹介` → `## 規制フットプリント` — スコープ内 regime(GDPR、CCPA / CPRA / 他の州コンシューマプライバシー、GLBA、HIPAA、FERPA、COPPA、VPPA、CPNI 等)
- `## プライバシーポリシーのコミットメント` — 公開ポリシーから抽出されたコミットメント
- `## 出力 (Outputs)` — 出力フォルダパス、ポリシー文書場所、最終スイープ日

`## 出力 (Outputs)` が `[PLACEHOLDER]` を含むなら:
> 「出力がまだ設定されていません。直接照会チェックなら実行可能 — 何を計画しているか説明してくれれば、現行ポリシーに対して差分。クロールスイープを有効にするには、`/privacy-legal-ja:cold-start-interview` を実行し、出力フォルダパスを提供してください。」

`## 出力 (Outputs)` → **プライバシーポリシー文書** のパスから実際のプライバシーポリシー文書を読む。config CLAUDE.md のコミットメントは要約; 実際の文書が編集提案のための authority。

### プライバシーコミットメントは複数のサーフェスに現れる — すべてをスイープ

ウェブサイトのプライバシーポリシーは 1 つのサーフェス。現代のプライバシープログラムは規制機関が積極的に整合性を精査する少なくとも 4 つの場所で拘束的コミットメントを行う:

1. **Cookie 同意バナー / CMP。** Consent management platform は特定の cookie カテゴリと目的を約束。プライバシーポリシーが「分析 cookie を使用」と言い、CMP が「厳密に必要なもののみ」を提供するなら、抵触。EU DPA と FTC は CMP 誤設定に対し執行している。
2. **App store プライバシーラベル。** Apple App Privacy(「栄養ラベル」)と Google Data Safety は自己申告で FTC 執行可能。プライバシーポリシーを更新したのに App Store ラベルを更新しない会社は、規制機関可視の実質的不整合を持つ。チェック: ラベル最終更新はいつ? 現行ポリシーのデータカテゴリ、目的、共有と一致するか?
3. **アプリ内同意フロー。** ユーザーがデータ利用選択を実際に行う画面(オンボーディング同意、設定トグル、「ポリシーを更新しました」ダイアログ)。ポリシーはあなたがすることを述べる; 同意フローはユーザーが合意したことを述べる。一致すべき。
4. **セクター固有告知。** GLBA プライバシー告知、HIPAA NPP、FERPA ディレクトリ告知、COPPA 直接告知。これらは独自の更新義務と、一般プライバシーポリシーとの整合性要件を持つ。(下の「セクター告知」で詳述。)

**プラクティスプロファイルに各サーフェスの場所と最終更新日のフィールドを追加。** スイープは各々を現行ポリシーと比較し乖離をフラグ: 「プライバシーポリシー更新 [date]。App Store ラベル最終更新 [earlier date] — 新データカテゴリを反映していない可能性。CMP 最終設定 [date] — cookie 目的がポリシーと一致するか検証。」

クリーンなプライバシーポリシーと古い App Store ラベルを持つ会社は、FTC 苦情が起きるのを待っている会社。文書ではなくサーフェスをスイープ。

### セクター告知はこのスイープのスコープ内

ウェブサイトのプライバシーポリシーは 1 つの告知。連邦規制対象実務には、ウェブサイトポリシーが代替できない別のセクター固有告知が必要。`## 規制フットプリント` に以下が含まれるなら、スイープはウェブサイトポリシーに加えてその告知に対しても実務を差分 — またはそのような告知が設定されていないなら不在をフラグ:

| フットプリントエントリ | 差分対象セクター告知 | フラグすべきもの |
|---|---|---|
| **GLBA / Reg P**(NPI を扱う金融機関) | GLBA 初回 + 年次プライバシー告知(12 C.F.R. Part 1016 または機能規制機関の同等) | 新 NPI カテゴリ、非関連第三者との共有、Reg P 告知に反映されないオプトアウト機構の変更を示唆する出力。NPI を受領する分析ベンダーと署名された DPA で対応する Reg P 告知更新がないのはギャップ。 |
| **HIPAA**(covered entity または BA) | Notice of Privacy Practices(45 C.F.R. § 164.520) | 新しい用途や開示、新しいルーチンカテゴリ、患者権利機構の変更を示唆する出力。PHI を流す新サブコントラクターと署名された BAA で対応する NPP リフレッシュがないのはギャップ。 |
| **FERPA**(学校または学校サービス提供者) | 年次ディレクトリ情報 / 権利告知(34 C.F.R. § 99.37) | School-official 例外下のサービス提供者への新規開示カテゴリ、新しいディレクトリ情報要素、parental-consent フロースルーに影響する変更を示唆する出力。 |
| **COPPA**(13 歳未満向けサービス運営者) | 親への直接告知 + オンライン告知(16 C.F.R. § 312.4) | 子供から収集する新データカテゴリ、新しい第三者開示、verifiable-parental-consent 機構の変更を示唆する出力。 |
| **VPPA / CPNI / DPPA / その他セクター** | regime 固有の告知または同意 regime | 設定された告知に反映されない、regime が制限する処理活動。 |

**フットプリント内 regime にセクター告知が設定されていない場合**、各スイープで標準ギャップとしてこれを浮上 — 一度限りの発見ではなく。スイープ出力に含める:

> **セクター告知カバレッジ:**
> - [regime]: [設定された告知パス + 最終更新、または "NOT CONFIGURED — 解決まで毎スイープでフラグ"]

**スイープがセクター告知をロケートできない場合**、明示 — ウェブサイトポリシーのみに対する差分にサイレントフォールバックしない。GLBA を無視した policy-monitor スイープに依拠するフィンテック DPO は、警告なしに古い規制機関向け告知を出してしまう。ギャップを大声で浮上。

**フットプリントが曖昧ならユーザーに問う。** `## 規制フットプリント` が「GDPR / CCPA」を述べるが、出力スキャンが PHI、NPI、生徒データカテゴリを浮上させたら、進行前にフットプリントと実務のミスマッチを浮上: 「フットプリントは [GLBA / HIPAA / FERPA / COPPA] を列挙していませんが、このスイープは [category] を含む出力を見ています。この regime をフットプリントに追加すべきか、差分対象のセクター告知はあるか?」

## モード 1: スイープ

### スコープを決定

`## 出力 (Outputs)` → **最終ポリシースイープ** 日を読む。その日付以降の出力ファイルを出力フォルダでスキャン。日付未記録なら、全ファイルをスキャンし注記: 「初回スイープ — 全出力をスキャン中。」

出力フォルダが空または最終スイープ以降に新ファイルがないなら:
> 「[最終スイープ日] 以降の新出力なし。ポリシーは最近の実務と最新の様子。次回スケジュールスイープ: [date]。」

スイープ完了後、`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` の **最終ポリシースイープ** を今日の日付に更新。

### 各出力タイプで読むもの

**PIA(プライバシー影響評価):**
- 抽出: 処理されるデータカテゴリ、目的、関与する第三者 / 副処理者、保持期間、ユーザー権利への影響、処理に置かれた条件
- フラグ: 現行プライバシーポリシーコミットメントに無いもの

**DPA レビュー(署名済みまたは承認):**
- 抽出: 追加された副処理者、合意したデータ所在地、カバーされる処理目的、DPA 条項が作成したデータ主体への義務
- フラグ: ポリシーに記載のない副処理者(ポリシーが名指しするなら)、新処理カテゴリ、新データ所在地、ポリシーと矛盾する義務

**トリアージ結果(PIA REQUIRED / PROCEED 結果):**
- 抽出: 承認されたもの、公開コミットメントを暗示する条件(例: 「ローンチ前に影響を受ける当事者への開示が必要」)
- フラグ: ポリシーがカバーしない承認実務、ポリシー文言を要求する条件

**DSAR 応答:**
- 抽出: 以前の DSAR 応答に無かった新データカテゴリ、システムリストに追加されたシステム
- フラグ: 収集されているがポリシーに記載のないデータカテゴリ

### ギャップ識別

各フラグ項目について評価:

**REQUIRED 更新** — ポリシーがこの出力と矛盾するコミットメントをしている、または処理が発生していてポリシーが全くカバーしていない。更新しないことは実質的な誤表現を作る。

> 例: ポリシー「氏名、メール、支払情報を収集」。PIA で位置データ収集を承認。ポリシーは位置について何も言わない。これは REQUIRED 更新 — 開示していないデータを収集している。

**ADVISABLE 更新** — ポリシーは沈黙だが抵触はしない。処理は更新せずとも擁護可能、ただし更新したほうがクリーン。

> 例: ポリシー「サービスプロバイダーとデータを共有することがある」。新分析ベンダーと DPA 署名。ポリシーはベンダーを名指ししないが排除もしない。維持されているなら名指し副処理者リストに追加が advisable。

## 推奨文言の品質基準

ポリシー文言は:
- 既存ポリシーの voice とスタイルに一致(起草前に config CLAUDE.md サマリーだけでなく実際の文書を読む)
- 意味あるほど具体的、ただしルーチンの変更で壊れないほど具体的(「事業運営を支援するサービスプロバイダー」はベンダー全部命名より老けない)
- チームが守れないコミットメントをしない(例: アーキテクチャがそのデータを分析ベンダーに流すなら「位置データを共有しない」を起草しない)
- 文追加だけでなく、より広いポリシーポジション変更が必要な箇所をフラグ

起草時は常にどのセクションに追加するか述べる。正しいセクションが存在しないなら、そう述べて作成を提案。

## スケジュール統合

独自スケジューラー(カレンダー、タスクマネージャー、CI)で `/privacy-legal-ja:policy-monitor` を週次実行するリマインダー設定。スケジュール実行には scheduled-tasks 連携が必要、このプラグインに同梱されていません。

スイープが実行されるたびに、`~/.claude/plugins/config/claude-for-legal-ja/privacy-legal-ja/CLAUDE.md` の `## 出力 (Outputs)` → **最終ポリシースイープ** を更新するため、次回スイープは新ファイルのみを見る。

---

## 次のステップ・デシジョンツリーで締める

CLAUDE.md `## 出力 (Outputs)` の次のステップ・デシジョンツリーで締める。このスキルが生成したものに合わせてオプションをカスタマイズ — 5 つのデフォルトブランチ(X をドラフト、エスカレート、追加情報、様子見、その他)は出発点で、ロックインではない。ツリーが出力; 弁護士が選ぶ。

スイープが ~10 を超える乖離発見を浮上、またはユーザーが求めたいつでも: ダッシュボードを提案(CLAUDE.md `## 出力 → データの重い出力にはダッシュボード提案` 参照)。この出力に合わせて提案を形成 — サーフェス(ポリシー条項 / PIA / DPA / トリアージ)別カウント、重大度別カウント、ソースアーティファクトと推奨修復付きのソート可能発見グリッド。

## このスキルがしないこと

- ポリシー自体を更新しない — 推奨文言を起草し決定をフラグ、ただし人間がすべての変更をレビュー・承認。
- 規制変更を捕まえない — それは `reg-gap-analysis`。このスキルは内部実務乖離を監視、外部法的変更ではない。
- 出力が保存されることを強制しない — チームが PIA を設定フォルダに保存しなければスイープは見つけない。直接照会モードは保存出力なしでも動作。
- 非公式判断のためメールや Slack を読まない — 設定フォルダに保存された構造化出力のみ。
