# /cold-start-interview

1. `~/.claude/plugins/config/claude-for-legal-ja/legal-builder-hub-ja/CLAUDE.md` をチェック。populated な CLAUDE.md(`[PLACEHOLDER]` マーカーなし)が `~/.claude/plugins/cache/claude-for-legal-ja/legal-builder-hub-ja/*/CLAUDE.md` に存在するが設定パスにない場合は、設定パスにコピーし、何が移行されたかをユーザーに伝える。
2. Part 0(役割 + 統合チェック)を実行し、次に 5 つの質問(プラクティスタイプ、業界、チーム、ツーリングの慣れ)を、下記のワークフローに従って実行。
3. プロファイルをレジストリスキルとマッチング。スターターパックを推奨。
4. 推奨される各スキルの SKILL.md 要約を表示。ユーザーが選択。
5. 選ばれたスキルをインストール。`~/.claude/plugins/config/claude-for-legal-ja/legal-builder-hub-ja/CLAUDE.md` を(必要に応じて親ディレクトリを作成しつつ)書き込み — `## Who's using this`、`## Available integrations`、プロファイル + インストール済みリストを含む。

**`--check-integrations`:** Part 0 の統合可用性チェックのみを再実行。役割やプラクティスプロファイルに触れずに、`~/.claude/plugins/config/claude-for-legal-ja/legal-builder-hub-ja/CLAUDE.md` の `## Available integrations` テーブルを更新します。MCP コネクター追加・削除後に使用。

プローブ時: MCP ツール呼び出しが実際に成功した場合のみ ✓ をレポート。設定済みだが未テストのコネクターは ⚪ でマークし、確認方法の 1 行を添えます。`.mcp.json` 宣言だけで ✓ をレポートしてはいけません — 実際には接続されていないものを接続済みと思わせて誤解を与えます。

## コールドスタート確認

`~/.claude/plugins/config/claude-for-legal-ja/legal-builder-hub-ja/CLAUDE.md` を読む:
- **存在しない** → インタビュー開始。
- **`<!-- SETUP PAUSED AT: -->` を含む** → ユーザーに挨拶し、そのセクションから再開を提案。
- **`[PLACEHOLDER]` マーカーを含むが pause コメントなし** → テンプレートが完成していない。最初からやり直すか、プレースホルダーが始まる場所から再開するかを提案。
- **Populated(プレースホルダーなし、pause コメントなし)** → 既に設定済み。`--redo` がなければスキップ。

テンプレート構造は `${CLAUDE_PLUGIN_ROOT}/CLAUDE.md` にあり、セクション足場として使ってください。完成したプラクティスプロファイルを設定パスに書き出し、必要に応じて親ディレクトリを作成します。旧キャッシュパス `~/.claude/plugins/cache/claude-for-legal-ja/legal-builder-hub-ja/*/CLAUDE.md` に CLAUDE.md があるがここにはない場合、転送コピーします。

## 共有の会社プロファイルをチェック

`~/.claude/plugins/config/claude-for-legal-ja/company-profile.md` を探す。

- **存在する場合:** 読み込む。1 行の確認を表示:「あなたは[name]、[practice setting]、[company]所属、[industry]、[jurisdictions]で活動。合っていますか?(または「update」と言って共有プロファイルを変更。)」確認されたら会社の質問はスキップし、プラグイン固有の質問へ。
- **存在しない場合:** あなたはこのユーザーが最初にセットアップするプラグインになります。オリエンテーションとフォークの後、会社の質問を尋ね、共有プロファイルに書き出し(プラグインルートの `references/company-profile-template.md` のテンプレートに従う)、プラグイン固有の質問を続けます。ユーザーに伝える:「会社プロファイルを保存しました — 他の法務プラグインはこれを読み、これらの質問はスキップします。」

共有プロファイルに属する会社の質問(存在する場合は再質問しないこと): practice setting、会社名、業界、何を売っているか、規模、法域、規制当局、リスク選好、エスカレーション名。プラグイン固有の質問(プレイブックの立場、レビュー枠組み、ハウススタイル、監督モデルなど)はプラグインごとに残します。

## 目的

このプラグインはアプリストアです。コールドスタート・インタビューはオンボーディング・レコメンデーション・エンジンです — 何をするかを尋ね、スターターパックを推奨し、選ばれたものをインストールします。

他のコールドスタートと異なり、これは短いです。5 つの質問、推奨、完了。

## クイック / フルを選んでもらった後

ユーザーが選んだら、オリエンテーションを行います。あなた自身の声で次をカバー:

- **このプラグインが維持するもの:** プラクティスプロファイル(信頼ソース、更新設定、展開コンテキスト)、インストールをゲートする `allowlist.yaml`、インストールログ。
- **このセットアップが行うこと:** コミュニティ法務スキルの発見・インストール・評価を支援 — プラクティスプロファイルに基づくスターターパックと、ワークフローに触れる前のデザイン品質チェック。プラクティスプロファイルと更新設定を学習し、プラグインが毎回読むプレーンテキストファイルに書き出す。すべては後で変更可能。
- **データソース:** セットアップはユーザーの回答からのみフレッシュなプラクティスプロファイルを構築。個人の Claude 履歴、他の会話、ホームディレクトリの CLAUDE.md を読みません。会話の前段で関連する情報(例: ユーザーが事務所やチームに言及)があった場合は、組み込む前に尋ねます。ユーザーが入力または承認しない限り、何も設定に追加されません。

**なぜ重要か。** ハブのスターターパック推奨と auto-updater のフィルタリングはどちらも、このインタビューが書き出すプロファイルから読みます。汎用的なプロファイルは汎用的なスターターパック — もっともらしく有用だがユーザーの実際のプラクティスにマッチしないスキル — を得ます。ユーザーがどんな弁護士で、最もよく何をするかをハブに伝えることが、「他の弁護士が作ったすべてのスキル」と「あなたの仕事に合うセット」の違いを生みます。回答が具体的であるほど、推奨はユーザー自身のもののように感じられます。

## インタビューのペース

- **答えはどこかに存在すると仮定する。** 質問が、たぶんどこかに書き留められている情報(会社説明、プレイブック、エスカレーション・マトリクス、スタイルガイド、ハンドブック、法域リスト、案件ポートフォリオ)を求めるとき、ユーザーに記憶からタイプさせる前に、リンクや貼り付けを促してください。「リンクか文書を貼り付けるか、簡略版を教えて」が、1 文を超えるものの既定の問い方です。書かれているものをユーザーに再タイプさせるインタビュアーは、インタビュアーの第一の仕事に失敗しています。

短いとはいえ、5 つの質問は様々です — プラクティスエリアと業界はタップで通れますが、「最もよく行う仕事は何か」はちゃんとした答えが必要です。質問に簡単なタップ以上が必要なとき:

- **質問してから待つ。** 明示的に言う:「これはタイプして答えてください — 待ちます。」ユーザーが応答するまで次の質問に進まないでください。
- **何かがスキップされた場合:** 「今はスキップして、プロファイルにフラグを立てます — 後で `--redo` で埋められます。」進みますがスキップを追跡します。
- **プロファイルを書きスターターパックを推奨する前:** いずれかの回答がスキップされたり placeholder のままであれば、それらを列挙して尋ねる:「今埋めますか、placeholder のままにしますか? スターターパック推奨はプロファイルの質と同じです。」待つ。
- **決して** サイレントなギャップ付きでプロファイルを書かない — すべてのプレースホルダーは、ユーザーが確認した意図的なスキップであるべき。
- **バッチサイズ — サブパートをカウント。** 「1 ターンに 2〜3 個以上質問しない」は、サブパートを数えて 2〜3 個の *回答可能なプロンプト* を意味します。5 つのサブパートを持つ 1 つの質問は 5 つの質問です。テスト: ユーザーはスクロールせずに答えられるか? 質問が 1 画面に収まらないなら多すぎます。可能なら構造化されたタップ・スルー質問を好む — スクロールやタイプを必要としません。
- **ポーズと再開。** ユーザーに前もって伝えてください:「停止したい場合は「pause」(「stop」、「ちょっと後で戻る」)と言えば、進捗を保存します。後で `/legal-builder-hub-ja:cold-start-interview` を再実行すると、中断したところから続けます。」ユーザーがポーズしたら、`~/.claude/plugins/config/claude-for-legal-ja/legal-builder-hub-ja/CLAUDE.md` に部分設定を書き、トップに `<!-- SETUP PAUSED AT: [section name] — run /legal-builder-hub-ja:cold-start-interview to resume -->` コメントを、未回答フィールドには `[PENDING]` マーカーを(`[PLACEHOLDER]` とは区別)書きます。セットアップが再実行されてポーズされた設定を見つけたら、ユーザーに挨拶:「お帰りなさい。[section]で中断しました。前の回答は保存されています。続きから始めますか、最初からやり直しますか?」既に答えた質問を再質問しないでください。

**ユーザーが述べた法的事実はセットアップ中に出てきたときに検証する。** ユーザーがインタビューの質問に具体的な規則引用、制定法番号、判例名、期限、閾値、法域、または登録番号で答えた場合 — それが正気度をチェックできるなら — 設定に書き込む前にチェックしてください。彼らが言ったことがあなたの理解や貼り付けてもらったものと矛盾するなら、表面化させる:「閾値が X とおっしゃいましたが、私の理解では Y です — プロファイルにどちらを入れるか確認できますか? `[premise flagged — verify]`」CLAUDE.md に書かれた間違った事実は、その後の出力すべてに伝播します。ここで捕まえることは、製品で最もレバレッジの高い瞬間の 1 つです。

## インタビュー

### Opening

> コミュニティ法務スキルを見つけてインストールするのを手伝います — 他の弁護士が作って共有したものです。まず、あなたはどんな弁護士ですか? スタートパックを推奨します。

### Part 0: このプラグインを使うのは誰か、そして何が接続されているか

プラクティスプロファイルの前に簡単な 2 つの質問。これはプラグインができることではなく、どう動くかを形作ります。

#### このプラグインを使うのは誰?

> 日常的にこのプラグインを使うのは誰ですか?(これは、インストールするすべてのプラグインに引き継がれる Role シグナルを与えます — 非弁護士モードを持つスキルはここから読み、再質問しません。`recommend` と `qa` 出力は、適切な場合に非弁護士の読み手向けに構造化されます。)
>
> 1. **弁護士 or 法務担当者** — 弁護士、パラリーガル、弁護士監督下のリーガルオペ。
> 2. **弁護士アクセスのある非弁護士** — 創業者、ビジネスリード、契約マネージャー、HR、調達; 相談できる社内 or 外部弁護士がいる。
> 3. **通常の弁護士アクセスがない非弁護士** — あなたが自分で対応している。

回答が 2 or 3 の場合、一度だけこう言う:

> このプラグインはスキルの発見とインストールを行います。インストールするスキルは、あなたの役割に基づく独自のガードレールを持ちます — 私はあなたの回答を引き継ぐので、プラグインごとに答える必要はありません。

回答が 3 なら、次を追加:

> 弁護士、ソリシター、バリスター、その他の認可された法律家が必要な場合: 専門規制当局の紹介サービスが最も早い出発点です(米国の州バー、英国・ウェールズの SRA / Bar Standards Board、スコットランド / NI / アイルランド / カナダ / オーストラリアの Law Society、または各法域の同等機関)。多くが無料 / 低料金の初回相談を提供します。スモールビジネスには、地元のロースクール・クリニックや SCORE メンターが方向性を示せます。個人には、リーガル・エイド団体が多くのプラクティスエリアをカバーします。

#### 何が接続されているか?

> このプラグインは次と連携できます: Slack(新規スキル / 更新通知)。どのコネクターが設定されているかをチェックさせてください — 必要な機能は動作し、コネクターのない機能はサイレントに失敗するのではなくマニュアルフォールバックします。

**設定ではなく、実際に接続されているものをチェック。** `.mcp.json` に列挙されたコネクターは *available*。実際に応答するコネクターは *connected*。これらは異なり、混同すると信頼が壊れます。このプラグインが使用する各コネクターについて:

- 接続をテストできる場合(list や search のような簡単な MCP ツールを呼ぶ)、応答が成功した時のみ ✓ をレポート。
- テストできない場合(ここからプローブできない)、⚪「設定済みだが未検証 — MCP 設定を開いて確認」を 1 行の how-to と共にレポート。
- 設定だけで ✓ をレポートしてはいけません。

接続されていないと表示されるコネクターについて、ユーザーに接続方法を伝えます。例: 「Slack が接続されていません。Claude Cowork: Settings → Connectors → Add → Slack → サインイン。Claude Code: Slack MCP を設定に追加するか `/mcp` 経由で。このプラグインはそれなしでも動作します — 更新通知は能動的ではなく、次の `/legal-builder-hub-ja:registry-browser` または `/legal-builder-hub-ja:auto-updater` で表示されます — 接続すれば通知がリアルタイムになります。」

結果は次の形式でレポート:

> - ✓ [統合] — 接続済み(テスト済み)
> - ⚪ [統合] — 設定済みだが未検証。MCP 設定を開いて確認してください。
> - ✗ [統合] — 見つかりません。[Feature] は [manual alternative] にフォールバックします。[How to connect.]

これは必須ではありません。コア機能 — ブラウズ、インストール、QA、更新 — はファイルアクセスのみで動作します。

Part 0 の回答をプラグイン設定の `## Who's using this` と `## Available integrations` に書きます。このプラグインは `## Who's using this` を書くので、後でインストールされる他のプラグインはここから役割を読めます。

5 つの質問の前に: 「監視するコミュニティスキル・レジストリのリスト、またはチームが使用するスキルソースの許可 / 拒否リストはお持ちですか? 内容を貼り付け、ファイルパスを共有、または「いいえ」と言ってデフォルトを追加します。共有していただければ、再タイプさせるのではなく、それを読み、レジストリと許可リストをプロファイルに追加します。(これは /legal-builder-hub-ja:skill-installer に与えられます — インストーラーは何かを取得する前に `allowlist.yaml` を読み、restrictive モードでリストにないソースをブロックします。)」

**Deployment context(展開コンテキスト)。** 許可リストの質問の後、ファイルを書く前に尋ねる:

> 「インストールしたスキルをどう使いますか — 自分のためだけ、事務所で共有、または出荷する製品 / サービスに埋め込み?(Personal / Firm-internal / Product-embedding。)(これは `allowlist.yaml` に与えられます — 展開コンテキストが `licenses:` リストを種付けし、/legal-builder-hub-ja:skill-installer はそのリストにないライセンスのスキル取得を拒否します。)これでライセンスのデフォルトが設定されます。ほとんどのオープンソース・ライセンスは個人利用には問題ありません。Firm-internal はファイルレベル・コピーレフト(LGPL、MPL — 配布しない場合は OK)を追加します。Product-embedding は厳格です: 強コピーレフト(GPL、AGPL)は出荷前に法務レビューが必要な義務を作るので、デフォルトではなくフラグされます。」

回答を `## Sources I trust` の下にプロファイルに `Deployment context: [personal | firm-internal | product-embedding]` として記録。下記の許可リスト `licenses:` 種付けはここから読みます。

**プロファイルだけでなく `allowlist.yaml` にも許可リストを書く。** インストーラーのゲートは `~/.claude/plugins/config/claude-for-legal-ja/legal-builder-hub-ja/allowlist.yaml` から読み、CLAUDE.md からは読みません。回答をプロファイルにのみ記録すると、ユーザーが何を言っても、インストーラーは空の許可リストを見て permissive にフォールバックします — 看板の構造的防御をサイレントに敗北させます。この質問の後:

1. 設定パスに `allowlist.yaml` を書き、`skill-installer/references/allowlist.md` のスキーマに従う:
   - `mode:` — テンプレートのデフォルトは `restrictive`(fail-closed)。IT がキュレーションした公開元リストを持たない Solo / 小規模事務所には `permissive` を提案します(さもないと restrictive はすべてを拒否します)。Midsize / 大規模事務所、インハウス、政府には `restrictive` のまま(セキュリティポリシーが厳しいゲートを望むため)。常に確認:「許可リストを [mode] に設定します。Restrictive は追加するまで未知のソースを拒否します — 最も安全ですが、新しい公開元ごとに承認が必要です。Permissive は未知のソースをフラグしてインストール前に確認します — より便利、より厳格でない。どちらが良いですか?」明示的な同意なしに permissive を書かないでください。
   - `registries:` — ユーザーが提供したもの + デフォルト。
   - `publishers:` — ユーザーが名指しした、または信頼されたレジストリを所有する GitHub オーナー / org。
   - `connectors:` — ユーザーがリストを提供しない限り空; restrictive モードでは尋ねる:「Restrictive モードはコネクター許可リストが必要です — 承認済みの MCP サーバー URL を貼り付けるか、空のままにすればコネクターを宣言するスキルはすべて拒否されます。」
   - `licenses:` — 上の展開コンテキストの回答に基づいて種付け:
     - **Personal** → `MIT`、`Apache-2.0`、`BSD-2-Clause`、`BSD-3-Clause`、`ISC`、`CC0-1.0`。
     - **Firm-internal** → Personal と同じ + `LGPL-2.1-only`、`LGPL-3.0-only`、`MPL-2.0`。
     - **Product-embedding** → Personal と同じ。また `allowlist.yaml` のトップに次のコメントを書く: `## 出荷前にライセンスレビューが必要 — このリストにないものは法務サインオフが必要。` 強コピーレフト(GPL、AGPL)はここのデフォルトから意図的に除外 — それらを追加するには意図的な編集が必要。
2. プロファイルの `## Sources I trust` セクションにも要約し、人間がポリシーを見られるようにする。
3. ユーザーに保存場所を伝える:「許可リストは `~/.claude/plugins/config/claude-for-legal-ja/legal-builder-hub-ja/allowlist.yaml` にあります。インストーラーは何かを取得する前にこれを読みます。」

ユーザーがレジストリ / 許可リストファイルをアップロードした場合: 読んで、レジストリ URL と許可リスト / 拒否リスト エントリを抽出し、何を見つけたか確認し、スキーマに従って `allowlist.yaml` を書き、プロファイルに要約します。

**Freshness reminders(最新性リマインダー)。** 許可リストの質問の後(展開コンテキストが設定されている)、5 つの質問の前に尋ねる:

> 「コミュニティスキルが参考資料 — 規制、制定法、手続きテンプレート — をバンドルするとき、現行性を verify するよう促す前にどれくらい信頼すべきですか?(規制コンテンツは 6 か月が一般的なデフォルト。手続き / 様式コンテンツは 12 か月。変化が早い領域で働くならもっと短く設定。)」

単一の数(regulatory に適用、他は下記のカテゴリーデフォルトを使用)またはカテゴリーごとの回答を受け付ける。各回答を `N days`、`N months`、`N years` の形(`N` は正の整数 ≤ 120)に検証 — フリーフォームの散文は拒否して再質問。

回答をプロファイルの `## Freshness reminders` セクション(`## Sources I trust` の後、`## Installed starter pack` の前に挿入)に書く:

```markdown
## Freshness reminders

| Content category | Max age before reminder | Rationale |
|---|---|---|
| regulatory | 6 months | 規制当局は頻繁に更新; 執行優先事項は変わる |
| procedural | 12 months | 裁判所規則と手続きはよりゆっくり変わる |
| stylistic | 24 months | ハウススタイル、フォーマットテンプレート |
| unknown | 3 months | freshness を宣言しないスキルは慎重に扱う |

スキルの `last_verified` + `freshness_window` が過ぎた、またはユーザーの閾値(上記)が過ぎた — どちらか厳しい方 — のとき、skill-installer は実行前に警告を表示します。
```

ユーザーがより厳しい数値を与えた場合は、デフォルトの代わりにそれを書きます。「デフォルトを使う」と言われた場合はテーブルをそのまま書きます。

**ユーザーがレジストリリストをアップロードしなかった場合:** 5 つの質問の後、提案する:「監視対象レジストリと更新設定を、チームと共有できる独立したポリシーノートにまとめましょうか? プロファイルに保存するのと同じ内容ですが、チームメイトや新しいビルダーが、どのソースを信頼してどう更新を扱うかを見られるよう書式化されます。」

### 5 つの質問

1. **プラクティスエリア** — インハウス or 事務所? 商取引、プライバシー、プロダクト、雇用、訴訟、M&A、その他? (これは /legal-builder-hub-ja:related-skills-surfacer に与えられます — プラクティスエリアはスターターパックにマップする主キーです。)

   **箱に収まらないプラクティス。** ユーザーのプラクティスが選択肢に合わない場合(国際仲裁、公共国際法、amicus 専門、学術コンサル、プロボノパネル、tribal court、軍法、海事、または標準カテゴリが想定しない何か)、提案する:「あなたのプラクティスは私の通常のカテゴリに合わないようです。自分の言葉で教えてください — 何をしているか、誰のために、どの法域とフォーラム、仕事はどう見えるか — 合わない箱に押し込む代わりに、それからプロファイルを作ります。適用できない質問はスキップまたは適応します。」その後、フリーフォーム説明からプロファイルを作り、テンプレートのどのフィールドが埋められ、適応され、適用不可で空のままにされたかをフラグします。無理に当てはめたプロファイルは、本当のことから作った疎なプロファイルよりも悪いです。

2. **業界** — テック、ヘルスケア、金融、その他、関係なし? (これは /legal-builder-hub-ja:related-skills-surfacer と /legal-builder-hub-ja:registry-browser に与えられます — 業界はスターターパックを絞り、レジストリ結果をフィルタします。)

3. **チーム規模** — Solo、小チーム(2〜5)、大法務部? (これは `allowlist.yaml` モードのデフォルトに与えられます — Solo / 小は permissive、Midsize / 大 / インハウス / 政府は restrictive。)

4. **最もよく行う仕事は?** — 契約レビュー、コンプライアンス、ローンチレビュー、ディールサポート、ブリーフライティング等。(これは /legal-builder-hub-ja:related-skills-surfacer に与えられます — surfacer は、コミュニティにスキルがあるものをしているときに促します。)

5. **ツーリングの慣れ** — ビルダー(自分でスキルを書く)、いじる人(インストール済みを編集)、とにかく動かしたい派(箱から出してすぐ動いてほしい)? (これは /legal-builder-hub-ja:related-skills-surfacer に与えられます — ビルダーは raw レジストリと /legal-builder-hub-ja:skills-qa フレームワークを取得; とにかく動かしたい派はキュレーション済みの動くパックを取得。)

### Recommend(推奨)

プロファイルをレジストリスキルにマップ:

| プロファイル | スターターパック |
|---|---|
| インハウス商取引、テック | commercial-legal プラグイン + lpm-skills(案件インテーク、スコープ管理) |
| プライバシー・カウンセル | privacy-legal プラグイン + コミュニティ DPA / PIA スキル |
| プロダクト・カウンセル | product-legal プラグイン + コミュニティ・マーケティングレビュー・スキル |
| 事務所訴訟 | litigation-legal プラグイン + lpm-skills(案件計画、予算) |
| Solo / 小チーム | 軽量なものすべて — フルレビュー・スキルよりトリアージ・スキル |
| ビルダー | raw レジストリと skills-qa フレームワーク — 彼らは自分で作って検証する |

推奨される各スキルについて: SKILL.md の説明を表示。彼らに選ばせる — yes なしには何もインストールしない。
