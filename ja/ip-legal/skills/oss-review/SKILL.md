# /oss-review

`~/.claude/plugins/config/claude-for-legal-ja/ip-legal-ja/CLAUDE.md` のプラクティスプロファイルに照らしてオープンソース・ライセンス・コンプライアンス・チェックを実行します。依存関係をライセンス・ファミリーで分類し、デプロイモデルに対して義務をマッピングし、ライセンス不明やオープンソースを装う非 OSI パッケージをフラグし、アクション(コンプライアンス、置換、削除、法務レビュー、商用ライセンス取得)を推奨します。

## 指示

1. **`~/.claude/plugins/config/claude-for-legal-ja/ip-legal-ja/CLAUDE.md` をロード.** プレースホルダーがあれば停止して促します: 「先に `/ip-legal-ja:cold-start-interview` を実行してください — レビュー前にプラクティスプロファイル(あれば OSS ポリシー)を学ぶ必要があります」。プラクティスプロファイルがアップロード済み OSS ポリシーを指すなら、それも読みます — このチームでの accepted / review / banned ライセンスのソース・オブ・トゥルース。

2. **スコープを確立:** 依存リスト(package.json、requirements.txt、go.mod、Gemfile、Cargo.toml、pom.xml、SBOM)、単一ライブラリ、または公開準備中の外部公開コード。ユーザーがパスを渡したらファイルから推測、そうでなければ尋ねます。

3. **義務を分類する前にデプロイモデルを確立** — SaaS、配布バイナリ、内部のみ、または埋め込み。同じ依存リストでも、これにより異なる義務がトリガーされます。

4. **下記のワークフローに従います.** 特に:
   - 実際のライセンス本文を読み、メタデータだけ見ない — LICENSE ファイルは間違っている可能性、パッケージメタデータは古い可能性。
   - 各パッケージを permissive / weak copyleft / strong copyleft / public domain / non-OSI / unknown に分類。
   - ライセンス不明をデフォルトで permissive ではなく「needs review」とフラグ。
   - 非 OSI ソース利用可能ライセンス(SSPL、BUSL、Commons Clause、Elastic License、fair-source)をフラグ — これらはオープンソースではない。
   - 外部公開コードでは、選択した outbound ライセンスがすべての埋め込み依存関係と互換であることをチェック。

5. **メモを下記テンプレートで出力** — work-product ヘッダーを最初、ボトムライン、メモ冒頭のフラグ、重大度別のパッケージ別ブロック、法域注記、outbound チェック(該当時)、承認ルーティング。

6. **決断スタンスを尊重.** コピーレフト・トリガー分析が争点(AGPL の「ネットワーク経由で対話」、GPL-3.0 の「conveying」、LGPL のリンクスコープ)に依存する場合、弁護士レビューのためフラグし、両方向に切れる要因を表面化します。strong copyleft またはライセンス不明としてフラグされたものは、依存関係が出荷されるかコードがリリースされる前に弁護士へ。

## 例

```
/ip-legal-ja:oss-review ~/code/my-project/package.json
/ip-legal-ja:oss-review ~/code/my-project/requirements.txt
/ip-legal-ja:oss-review redis
/ip-legal-ja:oss-review ~/code/my-project  # リポジトリルート — すべてのマニフェストをスキャン
```

## 接続するとより良く動く

OSS クリアランス要求は通常チケッティング・システム経由で来ます。Jira、Linear、Asana に接続すると、本スキルは: 受信 OSS リクエストを監視、チケットで直接ガイダンスを返答(不完全な情報のフラグ、リポジトリリンクを尋ねる、ライセンス・ファミリー分類を返す)、リクエスト横断でクリアランス・ステータスを追跡できます。

コネクターなしでは、チケットを貼り付けるかリクエストを記述してください。1 件ずつ扱います。チケッティング・コネクターを追加する方法は、リポジトリルートの `CONNECTORS.md` を参照。

## 案件コンテキスト

**Matter context.** プラクティスレベル CLAUDE.md の `## Matter workspaces` をチェック。`Enabled` が `✗`(インハウスのデフォルト)なら、この段落の残りをスキップ — スキルはプラクティスレベル・コンテキストを使い、案件機構は不可視です。有効でアクティブ案件がなければ問います: 「これはどの案件向け? `/ip-legal-ja:matter-workspace switch <slug>` を実行するか、`practice-level` と言ってください」。アクティブ案件の `matter.md` を案件固有コンテキストとオーバーライド用に読みます。出力は案件フォルダ `~/.claude/plugins/config/claude-for-legal-ja/ip-legal-ja/matters/<matter-slug>/` に書き込みます。`Cross-matter context` が `on` でない限り、他の案件のファイルを決して読まないこと。

## 目的

ユーザーの依存関係ツリーにどんなライセンスがあるか、コードがどうデプロイされるかを踏まえそのライセンスがどんな義務をトリガーするか、各々に何をするかを伝えます。出力は、弁護士(または弁護士アクセスを持つエンジニア)が対応できるメモ — コンプライアンス、置換、削除、法務レビュー、商用ライセンス取得。

**これは初回パスの分類です.** コピーレフト分析はデプロイモデル、リンクの度合い、法域、時には未だ法廷で試されていない法的問題(特に AGPL の「ネットワーク経由で対話」、GPL-3.0 の特許条項)に依存します。strong copyleft またはライセンス不明として分類されるものについては、依存関係が出荷されるかコードがリリースされる前に弁護士が評価します。スキルは見つけたものを報告し、弁護士が何をするか決めます。

## 前提条件: プラクティスプロファイルをロード

**依存関係をスキャンする前に、`~/.claude/plugins/config/claude-for-legal-ja/ip-legal-ja/CLAUDE.md` を読みます.** ない場合またはプレースホルダーが残っている場合は、停止して `/ip-legal-ja:cold-start-interview` を実行してください。プラクティスプロファイルから:

- このチームで OSS レビューを誰が所有するか(多くの場合エンジニアリング + 法務サインオフ)
- コピーレフト義務のエスカレーション・ルーティング
- 出力に付与する work-product ヘッダー

プラクティスプロファイルが OSS ポリシーをアップロード済みなら、それも読みます — チームが受け入れる、レビューが必要、または禁止されたライセンスのソース・オブ・トゥルース。

## ワークフロー

### Step 1: スコープは何?

尋ねます(またはユーザー提供から推測):

> 何をレビューしますか?
>
> 1. **依存リスト** — `package.json`、`requirements.txt`、`go.mod`、`Gemfile`、`Cargo.toml`、`pom.xml`、SBOM(SPDX / CycloneDX)、ロックファイル
> 2. **単一ライブラリ** — 追加を検討している 1 つの特定パッケージ
> 3. **自社コード** — オープンソース化を計画しており、何が埋め込まれているかをチェックしたい

分析パスが異なります:

- 依存リスト → すべてのエントリーを分類、義務をロールアップ
- 単一ライブラリ → 1 つのパッケージを分類、利用可能なら推移的依存関係も歩く
- 外部公開コード → 何が埋め込まれているか(直接および推移的)をチェック、選択された outbound ライセンスがすべての埋め込みライセンスと互換かをチェック、LICENSE / NOTICE ファイルが正しいかをチェック

### Step 2: デプロイモデルは何?

これはライセンスリストの後の最も重要な入力 — 同じライブラリでも、ソフトウェアの配信方法によって異なる義務を運びます。尋ねます:

> どうデプロイしますか?
>
> 1. **SaaS / ホストサービス** — ユーザーはネットワーク経由でアクセス、ユーザーに何も出荷しない
> 2. **配布バイナリ** — コンパイルされたコードをユーザーに出荷(デスクトップアプリ、モバイルアプリ、オンプレサーバー、CLI ツール)
> 3. **内部のみ** — 社内でのみ使用、外部に配布しない
> 4. **埋め込み / ファームウェア** — ハードウェアまたはクローズドシステムのファームウェアで出荷

| デプロイ | 実質的に問題になるライセンス |
|---|---|
| SaaS | AGPL(ネットワークトリガー)、UI 内の permissive な表示、競合サービスとして再配置するなら SSPL/BUSL/Elastic |
| 配布バイナリ | GPL、LGPL、MPL、EPL(配布でトリガー)、permissive 表示 |
| 内部のみ | ほとんどのコピーレフトはトリガーしない — 配布なし。permissive 表示は良いハイジーン。社外ユーザーがネットワーク経由で対話すれば AGPL は依然トリガー。 |
| 埋め込み / ファームウェア | GPL はここで特に難しい(ソース開示 + 再現可能ビルド + 場合によりインストール情報)。出荷後ではなく、出荷前に計画。 |

デプロイモデルを出力メモにフラグ — 「SaaS」vs「配布バイナリ」で同じ依存リストをレビューすると異なる義務になります。

### Step 3: 各依存関係を分類

各パッケージについて、ライセンスを判定。実際のライセンス本文を読み、メタデータだけを見ないこと — LICENSE ファイルは間違っている可能性(ファイルは MIT と言うが、ヘッダーは GPL と言う、README は Apache と主張するがライセンスファイルがない)、パッケージマネージャーのメタデータは古い可能性があります。

以下に分類:

| バケット | 例 | 主要義務 |
|---|---|---|
| **Permissive** | MIT、BSD-2-Clause、BSD-3-Clause、Apache-2.0、ISC、Zlib、Unlicense | 表示、ライセンス文書保持、Apache-2.0 は特許許諾 + NOTICE 要件を追加 |
| **Weak copyleft** | LGPL-2.1、LGPL-3.0、MPL-2.0、EPL-1.0、EPL-2.0、CDDL | ファイル単位またはライブラリ単位のソース開示。リンクルールは異なる |
| **Strong copyleft** | GPL-2.0、GPL-3.0、AGPL-3.0、OSL、EUPL(バージョンによる) | 広範なソース開示。AGPL はネットワーク使用に拡張 |
| **Public domain / dedication** | CC0、Unlicense、WTFPL | 通常義務なしだが、一部は public domain への dedication を認めない法域では争点 |
| **非 OSI ソース利用可能** | SSPL、BUSL、Commons Clause、Elastic License、Confluent Community、fair-source ファミリー | オープンソースではない — 商用利用、競合サービス利用、または両方を制限。個別ライセンスを読むこと。 |
| **その他 / カスタム / 不明** | ベンダー固有、プロパライエタリ、ライセンスファイル欠如、ファイルとヘッダー間のライセンスコンフリクト | 停止 — デフォルトで permissive として扱わないこと |

フラグ:

- **デュアルライセンスのパッケージ** — どちらのライセンスを使うか? 選択が義務を変える可能性。
- **非推奨パッケージ** — パッケージはもはやメンテナンスされていない。サポート対象の代替はあるか?
- **コピーレフト依存をツリーに持つパッケージ** — トップレベルのライセンスは permissive だが、推移的依存関係はコピーレフト。
- **最近ライセンスが変わったパッケージ** — Redis、MongoDB、Elastic、HashiCorp — ピン留めバージョンが思っているライセンス下にあることを確認。

### Step 4: 義務をデプロイモデルにマッピング

分類された各依存関係について、デプロイモデルが何をトリガーするかを述べる:

```markdown
### [package@version] — [License]

**Classification:** [Permissive / Weak copyleft / Strong copyleft / Public domain / Non-OSI / Unknown]

**Obligations for our deployment ([SaaS / binary / internal / embedded]):**

- [ ] [具体的義務 — 例: 「アプリと一緒に出荷する NOTICES ファイルに表示を含める」]
- [ ] [例: 「改変して配布する場合、改変部のソースを公開」]
- [ ] [例: 「AGPL ネットワークトリガー — ユーザーが私たちの改変版にネットワーク経由でアクセスする場合、ソースをユーザーに提供しなければならない」]

**Risk:** 🔴 Critical | 🟠 High | 🟡 Medium | 🟢 Low

**Recommendation:** [義務を遵守 | [代替] で置換 | 削除 | 出荷前に弁護士レビュー | [ベンダー] から商用ライセンス取得]
```

> **コピーレフト依存関係はどう消費されているか?** リンク関係がコピーレフトが実際にトリガーされるかを決定します。尋ねるか判定:
> - **静的リンク / 一緒にコンパイル:** 著作物が 1 バイナリに結合。コピーレフトがトリガーされる強いシグナル(LGPL「work based on the Library」、GPL 派生著作物)。
> - **動的リンク / 共有ライブラリ:** 著作物は実行時に分離可能。LGPL は明示的にこれを許可(「work that uses the Library」)。GPL の立場は争点(FSF は派生と言い、他は同意しない)。
> - **ヘッダー包含 / インライン関数:** どれだけ含まれるかにより派生著作物を作成できる。
> - **サブプロセス / IPC:** 明確に定義されたインターフェース経由で通信する別プロセス。通常は派生ではない。
> - **ネットワーク API 呼出:** ほとんどのライセンスでは、いいえ。**AGPL** では、ネットワーク対話条項により、ネットワーク経由でソフトウェアを提供することは配布です。マイクロサービス・アーキテクチャでは、API の背後にある AGPL コンポーネントは依然トリガーします。
> - **ファイルスコープ・コピーレフト(MPL):** 改変されたファイルのみがコピーレフトを運び、著作物全体ではない。コピーレフト・ファイルが改変されたかをチェック。
>
> **重大度評価はこれに依存します.** リンク分析なしの「LGPL — weak copyleft、リンクルールは異なる」は、エンジニアが訴えられる答えです。プロパライエタリ製品中の静的リンク LGPL は 🔴 Critical。動的リンク LGPL は 🟢 Low。同じライセンス、反対の評価。

**重大度キャリブレーション:**

| レベル | 意味 |
|---|---|
| 🔴 Critical | トリガーするデプロイでの strong copyleft(例: 配布バイナリでの GPL、SaaS での AGPL)。ビジネスモデルが実際に競合する非 OSI ライセンス(例: マネージドサービスを構築中の SSPL)。ライセンスが判定できず、パッケージが load-bearing。 |
| 🟠 High | チームが準備していない義務を持つ weak copyleft(ファイル単位の開示、NOTICE 要件)。選択ライセンスが曖昧なデュアルライセンス。ライセンスファイルとヘッダーが矛盾。 |
| 🟡 Medium | 表示要件があるがビルドに配線されていない permissive(NOTICES ファイル欠如、配布での LICENSE 欠如)。ライブラリの消費方法によりトリガーするしないが分かれる位置の推移的コピーレフト。 |
| 🟢 Low | 義務がすでに満たされている permissive。トリガーしないデプロイモデルのコピーレフト(例: 内部のみで再配布なしの GPL ライブラリ)。 |

### Step 5: 失敗モードをフラグ

以下を、メモ冒頭のセクションでコールアウト:

- **ライセンス不明** — permissive ではなく「needs review」と分類。未分類の依存関係は、出荷判断を停止すべきで、スルーさせないこと。
- **ライセンスファイルがファイルヘッダーと矛盾** — 両方を読み、矛盾を報告。
- **非互換組み合わせ** — GPL-2.0 only + Apache-2.0 は歴史的に既知の非互換。MPL / EPL / GPL 組み合わせを慎重にチェック。
- **オープンソースを装う非 OSI ライセンス** — SSPL、BUSL、Commons Clause、Elastic License、Confluent Community。ライセンスを読み、GitHub の「open source」バッジに頼らないこと。
- **ライセンス変更** — 以前のバージョンが permissive で現行版がソース利用可能なら、ピンが重要。

### Step 6: Outbound チェック(自社コードを公開前にレビューする場合)

ユーザーがコードを公開する準備中:

- 選択した outbound ライセンスがすべての埋め込み依存関係のライセンスと互換であることを確認(例: GPL コードを埋め込んだら MIT でリリースできない — 結合著作物は GPL でなければならない)
- LICENSE ファイルが存在し正しいことを確認
- NOTICE ファイルが存在し、必要な表示(Apache-2.0 など)をリストすることを確認
- 必要な場所で第三者ライセンス本文がバンドルされていることを確認
- リポジトリ履歴にプロパライエタリ・機密コードなし、顧客データなし、埋め込み資格情報なしを確認
- 任意のプロジェクト名の商標・ブランドポリシー(著作権ライセンスとは別)を確認

### Step 7: メモを組み立て

`~/.claude/plugins/config/claude-for-legal-ja/ip-legal-ja/CLAUDE.md` → `## Outputs` の work-product ヘッダーを付与します(Role により異なる — `## Who's using this` 参照)。

このメモとレビューされた任意の依存リストは特権付き、機密、または両方かもしれません。出力はソースからそのステータスを継承。特権サークル内でのみ配布。外部配布(特権サークル外のエンジニアリング・チケットに添付する前を含む)の前に work-product ヘッダーを剥がします。

> **No silent supplement.** 設定された法律調査ツールへのクエリーが、メモに必要なルール(ある法域での AGPL のネットワークトリガーの執行可能性、GPL-3.0 の特許許諾の範囲、最近再ライセンスされたパッケージの最新ライセンス本文)について少数のまたはゼロの結果を返す場合、見つかったものを報告して停止します。Web 検索またはモデル知識から尋ねずにギャップを埋めないこと。言ってください: 「検索は [tool] から [N] 件の結果を返しました。[rule / license / jurisdiction] のカバレッジが薄いようです。選択肢: (1) 検索クエリーを広げる、(2) 別の調査ツールを試す、(3) Web を検索 — 結果は `[web search — verify]` でタグされ、依拠前に一次資料でチェックすべき、または (4) 未検証とフラグして停止。どれにしますか?」 低信頼度ソースを受け入れるかは弁護士が決めます。
>
> **Source attribution.** メモがライセンス本文、ライセンスを解釈する裁判判決、またはスチュワード(FSF、OSI、SPDX、SFLC)からのガイダンスを引用する場所では、引用をタグします: `[OSI]`、`[SPDX]`、`[FSF]`、`[SFC/SFLC]`、`[Westlaw]`、またはコネクターから取得した引用には MCP ツール名。Web 検索引用には `[web search — verify]`。トレーニングデータから想起した引用には `[model knowledge — verify]`。リポジトリから直接読んだライセンス本文には `[user provided]`。`verify` でタグされた引用は捏造リスクが高い。タグを剥がしたり崩したりしないこと。

## 決断スタンス

ライセンスが自信を持って分類できない場合、**「needs review」とフラグ** — permissive と呼ばないこと。ライセンスリスクを過小分類するのは一方通行のドア: permissive デフォルト前提で下された出荷判断が、数ヶ月後にソース開示義務または差止になります。フラグ過多は両方向のドア — 弁護士がレビューでリストを絞ります。

同様に、コピーレフト・トリガー分析が争点(AGPL の「ネットワーク経由で対話」、GPL-3.0 の「conveying」、LGPL リンクの範囲)に依存する場合、弁護士レビューのためフラグし、両方向に切れる要因を表面化します。
